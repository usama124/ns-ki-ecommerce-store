# Manual InstaWorld COD booking and on-demand tracking

## Setup

Set server-only `INSTAWORLD_API_KEY` in `.env` locally and in Vercel's appropriate environment, then redeploy. Both env files have a blank placeholder. Use a merchant API **v2** key with shipment read/write access, not the legacy location key. No key is sent to the browser. Upstream URL is fixed to the documented production v2 host; this change makes no authenticated provider calls until an admin uses the new controls with a configured key.

Pickup addresses are managed in InstaWorld. In Orders dashboard → Details, move an eligible COD order to **Processing**, then use **Load pickup locations and serviceable cities**. Select an active account pickup, the exact matching destination and a positive per-unit item weight in kilograms. Confirm the COD total already shown in order details. Weight meaning/packaging treatment must match your merchant agreement; the application does not guess weights. Automatic courier selection is used and open parcel is off. Prepaid bookings, split shipments and automatic booking at checkout are not enabled.

Click **Book with InstaWorld** and accept the explicit real-shipment/cost confirmation. A successful response shows the assigned tracking number and courier status. Merely loading references or opening an order does not book anything. City names must match the stored order city apart from case/outer whitespace; unlisted towns and spelling aliases need address correction before attempting booking. Addresses exceeding the provider's 200-character limit must be corrected rather than truncated. Existing manual tracking and existing money-ledger entries block initial booking for reconciliation.

## Recovery and integrity

One durable record per order is kept under an `instaworld:booking:` _id in the existing private `nski_commerce_config` collection. Its native unique _id handles cross-instance duplicate claims without new collection/index initialization. It stores the immutable outgoing request, actor-independent attempt key, timestamps, credential fingerprint and tracking, not the API key. This collection contains private operational/customer information and is never exposed through a Payload collection API. Existing commerce initialization is required; no new initialization command or production database mutation was performed during implementation.

A short transaction fences the order and claims the booking; provider HTTP calls happen outside the transaction. Double clicks, concurrent admins and retries converge on the saved payload/key. Booking always checks reference and pickup location upstream before a create call. Matching remote amount and consignee are checked before linking an existing shipment. Multiple/incomplete matches, changed details, unknown outcomes and expired retry windows require reconciliation, not a new key. Provider keys last 24 hours; this integration conservatively stops resending after 23 hours. Frozen payloads are not silently edited. Changing the API key also blocks retry/refresh of old attempts until reconciliation; operational key rotation for existing shipments needs a reviewed migration, not guessing that a new credential belongs to the same account.

If a timeout or local persistence failure occurs after remote creation, use **Reconcile / retry saved booking**, never independently book a second consignment in the portal. An attempt persists even when failed. This first release intentionally has no reset/unlock/rebook/delete control: correction of a locked failed attempt requires a reviewed reconciliation. Provider-managed orders cannot be locally cancelled/deleted or have their addresses, items, totals or tracking edited through generic admin/REST routes. Manual order progression to shipped/delivered remains available. Provider cancellation and returns are not implemented; contact the courier/store operator rather than bypassing the guard. Future cancellation/rebooking must verify remote outcomes before releasing stock.

## Tracking

Admin **Refresh shipping status** calls the shipment-detail and history APIs. The existing customer Track Your Order page also refreshes a linked shipment only **after** its exact order/contact lookup and rate limit succeed. No arbitrary tracking-number proxy is public. Only tracking number, status codes, checked/recorded timestamps and sanitized history are returned; consignee, raw courier wording, settlements, API keys and booking payloads are excluded.

Refreshes share a durable per-order lease/cooldown of at least one minute, including upstream failures. Concurrent viewers reuse the snapshot. Timeout/provider errors retain the previous status and old last-checked timestamp; this is not represented as a successful live refresh. Older provider observations do not overwrite newer recorded status. Updates are on demand, not automatic background polling. There is no scheduler, webhook receiver or per-shipment interval. Large order volume may require an approved incremental account-wide sync instead of on-demand detail polling to stay within the provider's per-key quotas.

Shipment state is separate from the store's order state: BOOKED does not mark shipped, delivery failure/RTO does not restore stock, and DELIVERED does not record COD remittance. No automatic order-status emails or financial entries are emitted on courier refresh. Tracking is displayed in the dedicated InstaWorld panel and customer tracking result; it is not copied into the legacy manual fulfillment fields in this initial release. The store must explicitly mark dispatch/delivery through its existing controls. AWB download, settlement imports and automated reconciliation remain future work.

## Rollout and verification

Existing flat shipping, optional free shipping, payment switches, private receipt flow and new-order alerts are unchanged by courier booking. COD is not automatically enabled. Automated tests mock upstream HTTP and database boundaries; they do not validate real account scopes, actual provider acceptance, concurrency on a live replica set or charges. No real booking, live tracking fetch with a merchant key, cancellation, remittance or email was generated during implementation. Before production activation, configure the account key privately, verify weights/pickup/serviceability, and authorize one controlled real operational test (or obtain an InstaWorld sandbox). A production account test can incur charges.

Contract: [InstaWorld Merchant API v2](https://one-be.instaworld.pk/merchant-api/v2/docs), [OpenAPI](https://one-be.instaworld.pk/merchant-api/v2/openapi.yaml).
