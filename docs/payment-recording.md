# Actual payment and partial-refund recording

Implemented locally on 25 October 2026, following the historical-operations batch. Open **Reports → Recorded payments & refunds (actual money)**. This is an operational record of money already received/returned, **not a payment gateway or a refund execution service**. No production activation or money transfer is performed by this implementation.

## Activate and use

1. Release through the normal backup/staging/deployment workflow. Transaction-enabled MongoDB and initialized commerce infrastructure are required. There are no new environment variables, Payload schema fields, generated types or import-map entries in this batch. History/stock activation remains separate.
2. As an administrator, expand the payment section and click **Enable payment recording** once. Same-origin `POST /api/admin/payments/initialize` explicitly creates private native collections/indexes and a readiness marker. Reads never create them implicitly. Review index creation under the usual production change process. Repeating setup does not reset entries or balances.
3. Enter a Karachi report date range and, for recording, the database **order ID**, then load the report. Existing order links in the standard Orders report lead to the Payload record containing its ID. Report dates select actual event occurrence, not placement/confirmation. A blank order ID reports all matching money events.
4. Check bank/courier/cash evidence, choose collection or refund, PKR amount, actual money method/reason and actual occurrence time, and confirm that money really changed hands. The time input uses **your browser timezone**; server storage/table/CSV timestamps use UTC. Do not enter merely promised payments. Up to two decimal places are supported using exact integer minor units internally.
5. A refund must reference the original **collection entry ID**, shown in the table. Earlier collections outside the current dates can be found by changing the date window; the 366-day window limit applies per query, not as a retention limit. Multiple partial refunds are supported.
6. Reload after a successful entry. The report separately shows date-filtered event totals and the selected order's all-time recorded collections/refunds. No records means **unknown historical payment coverage**, not proof that nothing was paid. Old payments are never inferred from status or receipts. Proven past events can be entered explicitly for an existing order, but must not predate order creation.

## Rules and safety

- A collection cannot make the order's **net recorded collected amount** exceed its stored total including fees. New collections on cancelled orders are refused; refunds of their previously recorded collections remain allowed. After a refund, a later genuine replacement collection may be recorded on a non-cancelled order, so lifetime collections can exceed one order total while the net cap remains enforced.
- Refunds cannot exceed the original collection's unrefunded amount or the order's net recorded collection. A refund cannot precede its collection. No future actual event more than five minutes ahead of server time is accepted. This clock-skew allowance is not an instruction to record future promises.
- Recording does not change order status, inventory, customer notifications, analytics purchase/refund events or courier settlement. Confirming/delivering a COD order does not record collection; cancellation never records a refund. Transfer verification remains separate too.
- Once an order has any money entry, its items, prices, fees and payment method are frozen, and it cannot be deleted—even after a full refund. Status, contact, notes and fulfillment edits remain separate. Use cancellation and retain the audit trail; do not rewrite financial terms to hide a discrepancy. An order amend/credit-note workflow is a later extension.
- Entries are immutable through the application. There is no edit/delete endpoint. Do not invent a monetary refund to correct a typing mistake if no money actually left the business. A separately reviewed bookkeeping reversal/correction workflow is not implemented yet. The `correction` refund reason still requires an actual return of money.
- Each submission has a stable UUID and canonical fingerprint including administrator identity. Replaying identical details returns the existing entry; reusing its key for different details is refused. Transactional order write fences serialize entries against each other and against order edits/deletion without changing order content/timestamps. Derived balances and entries commit/roll back together. Balance/ledger disagreement blocks further writes; do not reset balances or edit native collections to bypass reconciliation.

## Uncertain results

The browser saves a pending command in **sessionStorage before sending it**. A network error, HTTP 503 or conflict locks its details; retry sends exactly the same key/body. Closing/reopening the report section or reloading the same tab restores it and requires renewed operator confirmation. Successful recovery returns the existing entry instead of inserting another one. Explicit validation/limit refusals allow correction as a new submission.

Do not switch tabs/devices, clear browser storage, change accounts or create another key to bypass an unresolved outcome. The pending key is displayed for reconciliation. Session storage is tab-scoped and is not a cross-device synchronization/duplicate-payment detector; separate genuine-looking keys cannot be deduplicated reliably without provider reference integration. If storage is blocked, recording is refused before sending. Invalid stored recovery data blocks new recording until an administrator investigates. Do not blindly discard it. Durable backend replay remains available with the original key/body and original admin identity even if the browser's tab storage is lost.

## Reports and exports

- Event count, recorded collections, recorded refunds and **net recorded money movement** are aggregated across all matches, independent of the deterministic 50-row detail pages. A period can have negative net movement when its refunds relate to earlier collections.
- These totals are not profit, net sales, outstanding collectible COD or independently reconciled bank/courier settlement. Late historical entries can revise earlier periods. The existing placement-cohort reports retain their prior semantics and do not silently blend in this different date basis.
- Pagination/CSV uses the applied filters, not unsaved form edits. Dates are inclusive Karachi days, converted to UTC bounds, over 1–366 days. Separate reads are live observations, not an accounting snapshot lock.
- CSV covers all matches up to 5,000 rows. Larger exports fail with HTTP 413 rather than truncating. Amounts are labeled `amountPKR` with two decimals; timestamps are UTC. Spreadsheet formulas are neutralized.
- Export audit persistence is required before returning a file. Audits contain only actor ID, normalized filters, row count and time; they expire after 90 days via MongoDB TTL. The audit is not proof of a completed download. Event records have no automatic expiry; agree a retention/access policy for operational order/actor identifiers.

Every endpoint and native service requires an admin role. Mutations also enforce same-origin checks. Responses are private/no-store; aggregates are fixed and have a 10-second timeout. The application exposes no raw database stages or generic editing API for these private collections. Returned/exported fields exclude customer/contact/address, receipts, transaction references, free-form notes and internal fingerprints. Raw database changes bypass the application and require separate operational controls.

Implementation: `src/utilities/paymentLedger.ts`, `src/lib/payments/`, `src/app/api/admin/payments/` and `src/components/admin/ReportsView/PaymentsPanel.tsx`. Private native collections: `nski_money_entries`, `nski_money_balances`, `nski_money_exports`; readiness is `money-v1` in the existing commerce configuration collection.
