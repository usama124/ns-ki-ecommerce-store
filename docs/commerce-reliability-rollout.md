# Checkout, inventory, email and abuse-control rollout

Implemented locally on 24 October 2026. **Do not deploy this batch directly over an unprepared database.** No production database, infrastructure, scheduler or email provider has been changed. This is not full P0 or capacity sign-off.

## Implemented behavior

- Checkout requires an `Idempotency-Key` UUID-v4 header. The browser stores an opaque random key under a digest in session storage, retains it after failures/reloads with the same details, and blocks duplicate in-flight submissions. Delivery details are not stored in this new retry-key storage. Existing cart storage is unchanged. Changing checkout details creates a different intent; do not edit details or start another order while resolving an uncertain prior response.
- A native MongoDB record with a unique `_id` claims the key in the same transaction as the order, stock allocation, inventory movement and email outbox. The fingerprint binds normalized input, confirmed amount and authenticated account. Reusing a committed key with different details returns a conflict; a matching retry returns the original order even if current prices/stock have changed. The key is hashed in the DB; it is still a bearer-like retry capability and should not be logged. Records are not automatically expired into duplicate-eligible requests.
- Product/sale/shipping reads occur in the intended snapshot transaction. The current agreed grand total is still explicitly confirmed. A quote change creates no order, stock reservation or durable key claim. Snapshot prices are authoritative at transaction start, not a guarantee against a simultaneous later global-price change.
- The transaction helper refuses unsupported adapters, missing readiness initialization and inactive sessions. It retries bounded transient write conflicts and order-number collisions. Ambiguous commit results retry the same commit, never a fresh purchase body; the next request recovers by the durable key. A commit failure/timeout is **not** evidence that no order exists.
- New orders have system-owned `inventoryState` allocations, including actual units deducted and backordered units. Cancellation restores only deducted units. Repeat cancellation, reactivation and active item edits reconcile in one transaction. A private native movement collection records allocation changes. Deleting an active order is refused; cancel/reconcile first. Products/variants referenced by non-cancelled orders cannot be removed. Delivered orders remain non-cancelled historical references; archive products instead of deleting them.
- Existing stock adjustments now use the Inventory dashboard. Product creation can set initial stock; ordinary later product forms cannot overwrite stock with stale array values. The custom inventory endpoint reads/writes in a transaction and records a manual adjustment event. Admin batch operations are transactional **per order/update**, not all-or-nothing across the entire batch.
- Order hooks enqueue immutable email content within the DB transaction, rather than launching unawaited network calls before commit. Emails cover admin new-order alerts and customer receipt/confirmation, cancellation and shipment notices. Customer cancellation emails do not fall back to internal notes.
- Workers claim jobs with a lease, persist their delivery envelope before sending, use a stable provider idempotency key, back off failures, and mark exhausted/old ambiguous deliveries for human review. A `sent` queue state means provider acceptance, **not inbox delivery**. No automatic resend is attempted beyond the provider deduplication safety window; dead jobs require provider-side investigation before any manual resend.
- Shared MongoDB fixed-window counters protect checkout, exact order tracking, receipt uploads, order-link recovery, and non-admin REST/GraphQL registration/password recovery. Counters store HMAC identifiers instead of raw phones/emails/IPs, and expire through a TTL index. Local trusted provisioning/admin creation is not subject to the public registration limiter.

## Mandatory staging setup

1. Back up the intended database and review its actual adapter/replica-set configuration. This batch targets the current **MongoDB deployment**. SQL/SQLite checkout mutations fail closed rather than silently using weaker transaction behavior. A PostgreSQL `inventory_state` schema migration is included for schema compatibility only; it is not SQL purchase-integrity support, is not applied, and has not been DB-tested.
2. Prepare the release in a maintenance/staging environment. With its environment configured privately, run `pnpm commerce:initialize --allow-remote`. For a disposable localhost MongoDB URL, `--allow-remote` is unnecessary. This script explicitly creates the five `nski_*` internal collections, verifies/creates single-field unique order-number and digital-reference indexes, adds queue/movement/TTL indexes, and performs a real aborted transaction probe. It sets readiness false while preparing and true only on success. Duplicate historical references/numbers must be investigated, not silently deleted, to build unique indexes. Take a backup first; this command is an intentional DB/index write.
3. **Review legacy orders before rollout.** Old orders without `inventoryState` may continue normal status processing, but cancellation/reactivation/item edits are refused because actual historical backorder consumption is unknown. There is no automatic legacy backfill or reconciliation UI in this batch. Reconcile these orders under an approved, reviewed migration before enabling those operations. Do not assume every old item quantity was physically deducted and do not patch allocations by guesswork. This is a deployment blocker if existing staff need those operations immediately.
4. Set a random server-only `COMMERCE_WORKER_SECRET` of at least 32 characters in local/Vercel settings. The placeholder is in `.env` and `.env.example`. Confirm `RESEND_API_KEY`, `FROM_EMAIL` and `ADMIN_EMAIL`, a verified sending domain, and provider limits. The queue worker fails closed if these are missing; it never forwards failed customer mail to an arbitrary test/admin mailbox.
5. Provision an authorized scheduler to call `GET /api/admin/commerce/dispatch` with `Authorization: Bearer <COMMERCE_WORKER_SECRET>`. No scheduler has been created or billing plan changed. Each invocation processes at most three jobs with an eight-second provider-request timeout per job. Choose frequency/concurrency for the real order/email volume and provider quotas; one daily invocation is not an adequate continuous dispatcher. Without scheduling or manual dispatch, mail remains queued.
6. Staff can use **Check email queue** / **Dispatch queued emails** on the order dashboard. The admin-only summary endpoint `/api/admin/commerce` reports pending, processing, sent and dead counts without returning customer content. Manually dispatch via authenticated same-origin `POST /api/admin/commerce/dispatch`. Inspect dead jobs privately and reconcile provider history before replaying anything; do not blanket-reset their state.
7. Keep private receipt bucket configuration from [Private order receipts](private-order-receipts.md). The receipt upload limiter now also requires commerce initialization. Historical public receipts were not moved or purged.

## Rate-limit policy and edge assumptions

The fixed window is 15 minutes. Subject/IP limits are respectively: checkout 15/60, tracking 20/100, receipt 10/40, order-link recovery 5/20, registration 5/20, password recovery 5/20. Each action also has a fleet-wide accepted-attempt ceiling of 3000/window. A limited custom API response includes `Retry-After: 900`; windows are approximate abuse controls, not billing or capacity guarantees. These conservative constants need tuning against genuine traffic, shared networks and marketing campaigns.

Only Vercel's single-IP `x-forwarded-for` value is considered when `VERCEL=1`; elsewhere requests share an unverified-client bucket. Never silently trust caller-supplied `cf-connecting-ip`. When Cloudflare proxies Vercel, the observed trusted IP can be the proxy egress rather than each visitor; shared-IP limits may throttle legitimate users. Verify your real edge topology and origin-bypass policy before rollout, and configure provider-side WAF controls where appropriate. A DB-backed limiter is not a DDoS shield and still costs DB operations for rejected attempts.

See [Vercel request header behavior](https://vercel.com/docs/headers/request-headers) and [Resend idempotency retention](https://resend.com/changelog/idempotency-keys). The worker uses a 23-hour automatic-send cutoff rather than assuming provider deduplication lasts indefinitely.

## Privacy, operations and remaining work

The native collections are not public Payload collections and have no generated REST/GraphQL endpoints. Restrict DB access/backups accordingly: email snapshots contain customer information. Define approved retention policies for movement/outbox records and deletion/legal-hold procedures; no blanket TTL deletes purchase or email evidence. Only rate-limit windows have automatic expiry.

Order emails use the new Resend outbox. Payload's separate password-reset/order-access-email transport is **not reconfigured** by this batch; verify/configure its actual email adapter and delivery separately. Recovery throttling does not make an unconfigured transport deliver mail. Provider bounce/delivery webhooks, automated dead-letter alerting, reliable scheduler provisioning and provider inbox tests are also operational follow-ups. No real email was sent during testing.

No production initialization, SQL migration, legacy ownership/stock backfill, secret rotation, live R2 test or deployment was performed. Commercial hosting eligibility, region/pool budgeting, restore drills, private-cache/edge verification and realistic load testing remain before full P0 sign-off. No 500-concurrent-shopper claim is made.

## Tests

- The standard unit/integration suite uses mocks/local objects; `vitest.config.mts` does not include real DB tests.
- `vitest.commerce.config.mts` is an opt-in real MongoDB suite. It hardcodes only `127.0.0.1:27029/nski_commerce_test_20261024`, never loads `.env`, and cleans only that synthetic database. Run with `RUN_COMMERCE_DB_TESTS=1` against a disposable replica set. It is not a production test runner.
- `playwright.images.config.ts` runs isolated Chromium fixtures with mocked requests, including retry-key persistence across page reloads. Do not use the default DB-backed E2E configuration with production `.env`.

Local tests are a release aid, not a substitute for the staging setup and remaining operational checks above.
