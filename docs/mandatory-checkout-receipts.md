# Mandatory digital-payment receipts

Checkout now prominently displays a required receipt field and an Upload payment receipt button for Bank/Raast, JazzCash and EasyPaisa. Complete Order is disabled until a valid image is selected. COD is exempt, including when re-enabled by an administrator. Accepts JPEG, PNG or WebP up to 3 MB; the server reuses private receipt decoding/re-encoding and format/pixel limits, never trusting the filename or browser validation alone.

Digital checkout submits a bounded multipart request containing `checkout` JSON and one `receipt` file to `/api/orders`. JSON-only digital requests are rejected. COD retains JSON compatibility. The server validates receipt storage configuration and image content before creating the order, commits the existing order/stock/idempotency transaction, then conditionally uploads to the existing order-specific private R2 key. Success is returned only when receipt storage is confirmed. No schema/index changes are required.

MongoDB and R2 do not share an atomic transaction. If storage fails after order commit, the API returns `503 RECEIPT_UPLOAD_PENDING`, the saved order ID/number and its access token—not checkout success. The browser keeps the cart and retry identity, remains on checkout, and offers Retry Receipt Upload using the secure existing receipt endpoint, never another order submission. Ambiguous responses are checked using the authorized receipt-info endpoint. A full page refresh with unchanged checkout details retains the existing idempotency-key behavior. Do not restart checkout with changed details or a new key after a saved-order warning; use the secure order link/support if recovering outside that session. A saved pending-verification order can therefore exist without a receipt during an R2 outage; this is not a rolled-back purchase. There is no false claim of cross-system atomicity.

Existing receipts are never overwritten. Retried/concurrent uploads retain conditional writes, ownership checks and access tokens. Existing customer/admin receipt views continue to work. Order-created emails remain post-commit and may report the saved pending order before receipt recovery completes. Their failure does not roll back order placement. Existing legacy orders are not changed or backfilled. Admin order creation and verification policy are unchanged by this checkout-only change.

No production database records, receipts or real emails were created during automated verification. Deploy frontend and API together; old cached browser code submitting reference-only digital payments must refresh to use the required upload flow.
